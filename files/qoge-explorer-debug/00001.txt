  CHAIN MODEL

  Amount representation:  type Amount int64 (satoshis); SatoshisPerQOGE = 100_000_000; no float anywhere
  OutPoint:                {TxID string, Index uint32} — comparable, usable directly as a map key
  Input model:             one per raw vin — Index, PreviousOut (*OutPoint, nil iff coinbase), Coinbase,
                           ScriptSig, Sequence, Witness (WitnessStack); no address aggregation
  Output model:            one per raw vout incl. zero-value — Index, Value, ScriptPubKey, ScriptType,
                           WitnessVersion/Program, PubKeys (P2PK/multisig only), Address (Core-provided only)
  Transaction model:       TxID, Version, LockTime, Size/VSize/Weight, IsCoinbase, Inputs, Outputs,
                           Fee *Amount (nil in this phase — deferred)
  Block model:             Hash, Height, PreviousHash, MerkleRoot, Time, Bits, Difficulty, Nonce, Size,
                           Weight, TxCount, Transactions []Transaction — no consensus logic

  SCRIPT CLASSIFIER

  P2PK:              bare 33/65-byte pubkey push + OP_CHECKSIG — structural match; pubkey exposed on Result
  P2PKH:             OP_DUP OP_HASH160 <20> OP_EQUALVERIFY OP_CHECKSIG — exact 25-byte structural match
  P2SH:              OP_HASH160 <20> OP_EQUAL — exact 23-byte structural match
  P2WPKH:            witness v0, 20-byte program (via generic witness-program parser)
  P2WSH:             witness v0, 32-byte program
  P2QPK:             witness v2, 32-byte program — structural only, never from RPC "type" string
  NULLDATA:          OP_RETURN + push-only remainder (OP_PUSHDATA1/2/4-aware, bounds-checked)
  MULTISIG:          bare OP_m <pubkeys...> OP_n OP_CHECKMULTISIG, m/n validated against actual key count
  UNKNOWN_WITNESS:   any structurally valid witness program not matching the combinations above
  UNKNOWN:           everything else, including nil/empty/malformed input — never panics, never invents an address

There is also a smaller witness-classification mismatch: Core treats witness v0 with a length other than 20 or 32 as NONSTANDARD, while WITNESS_UNKNOWN is used only for unknown nonzero witness versions. I also caught one architecture issue before Phase 2B. We should store multisig participants for search/display, but not count the full output balance independently toward every participant. A clean solution is either output_participants, or an address relation with a role such as destination vs participant, with only destinations included in balance calculations.
