● Step 2 findings — fetch_file mechanics in depends/funcs.mk

  Read lines 28–41:

  define fetch_file_inner
      ( mkdir -p $$($(1)_download_dir) && echo Fetching $(3) from $(2) && \
      $(build_DOWNLOAD) "$$($(1)_download_dir)/$(4).temp" "$(2)/$(3)" && \
      ...
  endef

  define fetch_file
      ( test -f $$($(1)_source_dir)/$(4) || \
      ( $(call fetch_file_inner,$(1),$(2),$(3),$(4),$(5)) || \
        $(call fetch_file_inner,$(1),$(FALLBACK_DOWNLOAD_PATH),$(3),$(4),$(5))))
  endef

  fetch_file_inner builds the download URL as a flat concatenation: "$(2)/$(3)" — base path + / + filename, no package name or version inserted automatically. fetch_file's fallback attempt reuses the same filename ($(3)) against $(FALLBACK_DOWNLOAD_PATH), and FALLBACK_DOWNLOAD_PATH is one global Makefile variable shared by every package's fetch (confirmed — it's referenced by literal name inside fetch_file, not looked up per-package).

  This matches how upstream actually uses it: bitcoincore.org/depends-sources is a flat directory containing every package's tarball under its own filename, addressed identically for boost, liboqs, libevent, sqlite, etc.

  The QOGE GitHub release URL doesn't fit that shape. https://github.com/QOGE/qogecoin/releases/download/depends-boost-1.77.0/boost_1_77_0.tar.bz2 has a release tag (depends-boost-1.77.0) baked into the path between the host and the filename — that tag is specific to this one package+version. If I set FALLBACK_DOWNLOAD_PATH to that URL globally, fetch_file_inner would construct .../depends-boost-1.77.0/liboqs-0.15.0.tar.gz the moment liboqs or any other
  package's primary source ever failed — a URL that doesn't exist, silently breaking the fallback for every other package.

  Is there a per-package fallback hook? fetch_file hardcodes $(FALLBACK_DOWNLOAD_PATH) directly — no per-package fallback variable exists in funcs.mk. But $(1)_fetch_cmds is a ?= default, meaning any package .mk can override it outright. This repo already does exactly that — depends/packages/qt.mk:198 defines its own $(package)_fetch_cmds (to fetch three separate qt/qttranslations/qttools archives). That's a proven, working pattern in this exact codebase,
  not a hypothetical.

  Conclusion: a boost-specific override of boost_fetch_cmds is the architecturally correct fix, not touching the shared FALLBACK_DOWNLOAD_PATH. It keeps the QOGE-specific release tag scoped to boost, leaves every other package's fallback behavior untouched, and leaves FALLBACK_DOWNLOAD_PATH free to be fixed separately later as a real project-wide flat mirror if you ever stand one up.
